### Week 1 Objectives:

- Explain how Regions, Availability Zones, and shared responsibility affect application design and daily operations.
- Read IAM policies in terms of identities, actions, resources, conditions, and effective permissions.
- Trace network traffic through VPC routes and security controls instead of relying on subnet names.
- Choose EC2 compute, storage, and startup configuration according to workload and recovery requirements.
- Explain how applications obtain temporary AWS credentials through an EC2 instance role.
- Use CloudShell and Linux commands while keeping local permissions separate from AWS authorization.

### Week 1 Achievements:

- **Architecture and cost:** Connected Region/AZ choices to availability and ownership responsibilities. Recognized that a low-cost design also needs usage monitoring, timely cleanup, and awareness of costs outside instance runtime.
- **Access reasoning:** Can explain why a request is allowed or denied by examining its identity and policy scope. Prefer role-based temporary access and narrowly scoped permissions over distributing administrative credentials.
- **Network troubleshooting:** Can trace a connection through addressing, routing, and security rules. A public subnet label or an open port alone is insufficient evidence that an instance is reachable.
- **EC2 lifecycle:** Linked storage persistence and boot configuration to recovery planning. An instance can be replaced reliably only when required data and configuration are preserved outside its temporary runtime.
- **Credential handling:** Distinguished OS login access from an application's AWS API access. Using an instance role reduces key distribution, while metadata protections remain part of securing the host.
- **Command-line practice:** Established a habit of verifying identity, Region, file location, and permission scope before making changes, reducing confusion between local shell errors and AWS authorization failures.
