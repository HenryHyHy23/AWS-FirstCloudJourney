### Week 2 Objectives:

- Choose object, block, and shared file storage by access pattern, durability, recovery needs, and cost.
- Distinguish database availability, read scaling, and recovery instead of treating them as interchangeable.
- Explain Lightsail's management trade-offs and the roles of EFS, FSx, and server migration.
- Relate load balancing, health checks, and Auto Scaling to application capacity and state management.
- Interpret CloudWatch metrics and logs, then design alarms that produce useful operational responses.
- Explain hybrid DNS query paths and their dependency on working network connectivity.

### Week 2 Achievements:

- **Storage selection:** Can choose storage by access semantics and recovery needs, and explain why versioning, replication, and caching solve different problems. Retaining more copies also creates lifecycle and cost responsibilities.
- **Database design:** Can separate failover, read throughput, and historical recovery requirements. A resilient RDS design must account for replica lag, reconnect behavior, and the steps needed to use a restored database.
- **Service trade-offs:** Recognized when Lightsail's simpler operating model is sufficient and when a more configurable design is needed. Migration and shared storage choices should follow application dependencies and access patterns.
- **Elastic architecture:** Connected scaling policies to instance readiness, health checks, and externalized state. Adding instances only helps when the application can distribute work and survive instance removal.
- **Observability:** Can interpret a graph's aggregation and identify gaps in collection before drawing conclusions. Useful monitoring links a signal to investigation and response instead of producing notifications without context.
- **Hybrid DNS:** Can explain both query directions and identify the difference between DNS forwarding configuration and underlying connectivity. Redundant endpoints still depend on correct routing and authoritative DNS answers.
